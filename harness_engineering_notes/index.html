The theory of harnesses for AI agents

A language model is a next-token machine. An agent is that machine placed inside a loop that can act, observe, and stop. The harness is everything in that loop that is not the model.

Engineering notes Companion: notebooks/01_harness_from_scratch.ipynb

1. The claim

Most of what people call “agent intelligence” in production is not a special model. It is ordinary model capacity plus a carefully designed control program: prompts, tool schemas, permission checks, retries, memory, traces, and stop conditions. That control program is the harness.

The distinction matters. If you treat the model as the product, you tune prompts forever and still get silent loops, invented filenames, and unbounded tool use. If you treat the harness as the product, the model becomes a replaceable planner inside a typed, observable, policy-bounded process.

DEFINITION. An agent harness is the runtime that (1) constructs model context, (2) offers tools, (3) executes or refuses tool calls, (4) writes observations back into context, and (5) decides when the episode is over. The model proposes; the harness disposes.

This is the same idea as a process supervisor in operating systems, or a game loop in simulation: a thin, deterministic outer program around a rich, stochastic inner component. Reliability lives in the outer program.

2. Anatomy: model, agent, harness, environment

Four layers are easy to conflate. Keep them separate:

LayerWhat it isWhat it must not be
Model A function from messages (+ tool specs) to an assistant message. The source of truth for permissions, time, or filesystem state.
Harness The loop, registry, policies, context manager, tracer, stop rules. A pile of prompt text with no executable invariants.
Agent Harness + system prompt + tool set + model, aimed at a job. A chatbot with extra adjectives.
Environment The world tools can touch: repo, browser, APIs, tickets. Something the model can “imagine” into existence.

Historically the stack grew in public: chain-of-thought, then ReAct (reason + act interleaved with observations), then native function calling, then long-running coding agents (SWE-bench style scaffolds, IDE agents, terminal agents). The model improved, but the shape of the system stayed: propose action → execute → observe → repeat.

3. The control loop

Every serious harness is a while-loop with a budget. Pseudocode is the theory:

messages ← [system, user] for step in 1..max_steps: if context is too large: messages ← compact(messages) # harness owns memory assistant ← model.complete(messages, tools) append assistant if assistant has no tool_calls: return assistant.text # clean stop for each call in assistant.tool_calls: if policy.refuses(call): observation ← error(reason) # never throw out of the loop else: observation ← execute(call) # environment is real append tool message(observation) return timeout # budget stop

Three stop conditions cover almost all designs:

  1. Final text — the model emits no tool calls.
  2. Budget — max steps, max tokens, max wall time, max dollars.
  3. External halt — user cancel, CI timeout, sandbox death.

A fourth, rarer stop is goal detector: a verifier (tests, rubric, compiler) says the task is done even if the model wants to keep talking. Verifiers belong in the harness, not in the prompt.

INVARIANT. Tool execution is synchronous from the model’s point of view. The assistant message that requested tools is not “the answer.” The answer is whatever the harness returns after observations have been folded back in — or a structured failure if the budget expires.

4. Tools as a protocol, not a bag of functions

A tool is a contract with four parts: name, description (for the model), parameters (JSON Schema), and an implementation (for the runtime). The model never calls Python. It emits a tool call object. The harness binds that object to code.

Good tools are:

  • Narrow. read_file(path) beats do_anything(cmd) when you can afford it.
  • Observable. Return text the model can use next turn; include errors in-band.
  • Idempotent where possible. Retries are normal.
  • Side-effect labeled. Reads vs writes vs irreversible ops should be obvious to policy.

Errors must become observations, not exceptions that kill the process. Unknown tool names, bad arguments, timeouts, and policy refusals are all just strings in a role=tool message. The model’s next turn is how the agent recovers. The harness’s job is to make recovery possible and to bound how long recovery may take.

Parallel tool calls are an optimization, not a new theory: the harness may execute independent reads concurrently, then append several tool messages before the next complete(). Writes usually stay serial.

5. Context is a scarce, managed resource

The context window is not “memory.” It is a working tape with a hard length. Left unmanaged, tool output (logs, HTML, stack traces) will crowd out the goal. Context engineering is therefore a harness responsibility:

TechniqueWhen to use it
Truncation Tool payloads over a character/token cap; keep head + tail.
Offloading Write bulky artifacts to files; leave a path + summary in context.
Summarization Compress older turns into a rolling “state of the episode.”
Retrieval Pull only the files/tickets likely relevant to the current subgoal.
Pinned prefix System prompt, tool list, and non-negotiable policies always stay.

A useful mental model is attention as a budget. Every token you keep is a token the model might use instead of the user’s goal. Compaction is not an optimization bolted on later; it is how long episodes remain coherent.

6. Policy sits outside the prompt

System prompts can ask the model not to delete production. Only the harness can prevent it. Policy is a deterministic gate on tool names, argument size, paths, network, and credentials:

  • Allow-lists and deny-lists of tools.
  • Path jail (workspace root) for filesystem tools.
  • No secrets in traces; redact before logging.
  • Human approval for high-impact writes, if the product requires it.

Least privilege is the same as in ordinary software: give the agent the smallest environment that can still do the job. A coding agent in a throwaway worktree is a different creature from a chatbot with a live shell on your laptop.

7. If you cannot see the trajectory, you cannot improve it

An episode is a trajectory: messages, tool calls, latencies, token counts, stop reason. Tracing is not “nice to have.” It is how you debug an agent. Minimum viable trace:

  • run_start / run_end with stop reason and step count.
  • Each model turn (hash of prompt, number of tool calls, output tokens).
  • Each tool success or in-band error (name, duration, bytes returned).
  • Each policy block (the most important events in production).

Transcripts should be replayable: given the same mock model script (or recorded completions) the harness should produce the same sequence of tool executions. That property is what makes tests possible.

8. Evaluation is a second harness

You cannot unit-test “intelligence,” but you can unit-test the harness and score the agent:

  1. Harness tests — mock model, scripted tool calls, assert stop reasons, policy blocks, and error-as-observation. No network.
  2. Golden tasks — small environments with a known answer (on-call from a runbook, a failing test to patch).
  3. Rubrics / verifiers — tests pass, diff is small, citation exists in retrieved files.
  4. Regression suites — pin trajectories that used to fail; fail CI if stop_reason or safety gates change.

SWE-bench-style evaluation is this idea at scale: a harness checks out a repo, lets an agent patch it, and runs the project’s tests. The benchmark is as much a statement about harness quality (timeouts, patch application, isolation) as about the model.

9. Characteristic failure modes

FailureWhat you seeHarness response
Tool hallucination Call to a name that was never registered. In-band error listing valid names; do not crash.
Argument drift Wrong types, missing fields, huge payloads. Schema check; truncate; error string.
Looping Same tool, same args, no progress. Step budget; optional duplicate-call detector.
Context rot Model forgets the user goal under log spam. Compaction; pin the goal; offload blobs.
Premature stop Final text before tools were used. Prompting helps; eval catches it; optional “must-use-tool” tasks.
Over-acting Writes when a read would do. Policy; split read/write tools; approval for writes.

10. Design principles

  1. The harness is the product. Swap models; keep the loop, policies, and traces stable.
  2. Propose / dispose. The model may request anything; only the harness acts.
  3. Errors are observations. Recovery is a model turn. Collapse is a harness bug.
  4. Budgets are correctness. Unbounded loops are not “thorough,” they are unsafe.
  5. Context is curated. If the tape is dirty, reasoning will be too.
  6. Policy is code. Promises in English are not controls.
  7. Tools are small and typed. A sharp interface is easier to evaluate and to jail.
  8. Every run has a stop reason. final_text, max_steps, cancelled — never a shrug.
  9. Replay beats folklore. Scripted models make the loop testable.
  10. Eval the trajectory, not the vibe. Did it call the right tool? Did tests pass?
