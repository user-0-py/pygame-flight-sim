Practice questions on harness engineering

Multiple-choice items check definitions and failure modes. Subjective items ask you to design, debug, or evaluate a harness. Answers for MCQs are scored in the page; marking notes for written questions are behind a toggle.

Companion: theory worksheet Lab: notebook + MLflow

A. Multiple choice

Q1.

An agent harness is best described as:

The model proposes; the harness disposes. Prompts and schemas are inputs to that runtime, not substitutes for it.

Q2.

In a well-designed loop, a tool that throws FileNotFoundError should:

Errors are observations. Collapse of the loop is a harness bug. Budgets still bound retries.

Q3.

Which stop reason is not a harness decision?

Internal “I am done thinking” is not an executable stop. The harness stops on empty tool_calls, budgets, or external halt — optionally a verifier.

Q4.

A system prompt says “never delete production.” The model still emits rm_tree("/srv"). What actually prevents the delete?

Policy is code. Prompts request; gates enforce. Tracing records the block; it does not replace the block.

Q5.

Who owns context compaction (truncation, summarization, offloading)?

The context window is a working tape with a hard length. The harness curates it so the goal is not drowned in logs.

Q6.

You log success=1 because stop_reason=final_text, but the answer is factually wrong. What did you mix up?

The notebook’s MLflow lab splits success from task_correct for this reason. Agents can “finish” and still fail the job.

Q7.

In the MLflow mapping used in the lab, a nested run is the right place to record:

Parent run = episode (params, stop reason, transcript artifact). Nested run = tool span. Do not put secrets in traces.

Q8.

A golden-task eval for a file-research agent should primarily score:

Eval the trajectory and a checkable outcome. Harness tests (scripted tools, policy) are a separate, cheaper layer.

Q9.

The model emits a tool name that was never registered. The harness should:

Tool hallucination is a characteristic failure. Recovery is the next model turn; the observation must be honest.

Q10.

Why keep a step budget even when the model is “usually right”?

Budgets are correctness, not pessimism. The tiny-budget MLflow run is the lab’s demonstration.

Q11.

“Propose / dispose” means:

The assistant message that requested tools is not the answer. The environment changes only through harness-executed (or refused) calls.

Q12.

A replayable harness test uses a mock model because:

Replay beats folklore. Swap the mock for a vendor client later; do not rewrite the while-loop to “go to production.”

B. Subjective / design

Write answers on paper or in a notes app. Expand the marking note after you have attempted the question.

S1. Draw the loop (8 marks)

Write pseudocode for a harness loop with: system+user messages, optional compaction, model.complete, policy check, in-band tool errors, final_text vs max_steps. Annotate which lines the model is allowed to influence.

Marking note Award for: bounded for/while; compaction owned by harness; append assistant before tools; refuse-or-execute; tool messages on errors; two stop paths. Deduct if the model writes the filesystem directly or if exceptions escape the loop.

S2. Policy vs prompt (8 marks)

A coding agent has tools read_file, write_file, run_tests, and shell. Product requirement: it may not run shell on the host, only inside a disposable worktree, and must not read .env. Specify (i) prompt text you would still include, (ii) gates that must be code, (iii) one test you would write with a mock model.

Marking note (i) Job, style, “prefer tests over shell.” (ii) Deny-list or hide shell on host; path jail; block .env in read_file; maybe approve writes. (iii) Scripted read_file(".env") → observation starts with ERROR, no file bytes, policy_block in the trace/MLflow nested run.

S3. Failure mode (7 marks)

An agent lists a directory, then reads the same 2 MB log on every subsequent turn until the context fills and it forgets the user’s question. Name the failure, propose two harness changes, and say what MLflow metrics/artifacts you would inspect first.

Marking note Context rot / looping. Changes: truncate or offload tool payloads; duplicate-call detector; pin the user goal; step budget. Inspect: nested runs with repeated read_file and growing n_chars; parent steps; transcript.json tail vs system message.

S4. Two-layer eval (8 marks)

Design an evaluation plan for a “checkout on-call” file agent like the toy workspace. Split harness tests vs golden tasks vs a possible live-model smoke. State what would fail CI.

Marking note Harness: unknown tool, policy deny, max_steps, path escape — mock only. Golden: list then read RUNBOOK, answer contains on-call channel; task_correct. Live smoke: optional, not CI-blocking if flaky. CI fails on harness regressions and golden trajectory/verifier, not on prose style.

S5. MLflow experiment design (7 marks)

You want to know whether raising max_steps from 4 to 12 improves a 50-task file-QA suite. Describe parent-run params, metrics (including a verifier), how nested runs help debug a failing task, and one comparison you must not treat as causal without a controlled change.

Marking note Params: max_steps, tool set version, policy, prompt hash. Metrics: task_correct mean, success rate, steps, policy_block rate, latency/cost if available. Nested runs: which tool failed. Do not attribute a jump in task_correct to max_steps if the prompt and model also changed in the same experiment.

S6. Replace the model (6 marks)

List the interface of complete(messages, tools) -> assistant_message and argue in half a page why a vendor SDK should be an adapter behind that interface rather than the body of the while-loop.

Marking note Messages in, assistant with text and/or tool_calls out. Adapter serializes schemas and parses the vendor message. Loop, policy, compaction, MLflow stay stable so tests and traces remain comparable across models.

S7. Least privilege (6 marks)

Contrast three environments for the same “fix a unit test” job: (1) login shell on a laptop, (2) throwaway git worktree with read/write to that tree only, (3) read-only tools plus a patch applicator. Which harness is easiest to evaluate and why?

Marking note (1) unbounded blast radius. (2) standard coding-agent jail. (3) even narrower, easier replay and SWE-bench-like scoring (apply patch, run tests). Easier eval when the environment is small, resettable, and side effects are typed.

S8. Trace minimum (5 marks)

Write a checklist of events a production harness must emit for one episode. For each event, one field you would redact.

Marking note run_start/end (user text — redact secrets), model_turn (prompt — redact keys), tool_ok/error (return body — redact tokens), policy_block (arguments — redact paths with credentials). Stop reason and step count are not optional.
